# D-001 · 立项范围、原始反馈与路线图

## 用户原始需求

用户 2026-10-16 通过 `$govern` 明确要求「在工作区2开设一个新目标」，解决：

> 编排器自动调用负责独立审计的供应商时候，应当只允许向审计员输入形式审计命令“/audit <工作区编号> <目标编号>”或“/vision-audit <vp编号>”，而不允许编排器自行编写审计提示词，以避免编排器自行限制了审计范围导致交叉审计失去应有的独立视角的问题。

> 需要向用户询问信息时，如果可以，应该使用可以阻塞当前任务的询问卡片，等待用户答复后才能继续任务——如果卡片没有收到用户答复（比如卡片返回空答复）应该直接暂停任务（并阻塞当前目标——如果有的话），等待用户答复，而不允许自行在缺失用户答复的情况下继续推进（或以任何形式虚构用户答复内容）。

## 本轮立项处理

1. 在本区 Root 的 R3 下建立 GOAL-013，标题「独立审计命令派发与用户答复阻塞门禁」，slug `audit-dispatch-and-user-input-gates`，初始 active / 0%。Root、VP 和 Charter 的目的及边界不改。
2. 两项需求共同约束编排器的权限与门禁，合并为一个交付目标；按 P-001 先写 S1～S4 路线图（见 meta），不立即批量拆分子目标。
3. 本轮授权为立项与必要台账同步；未选择具体实现、审计 provider 或发布方案。用户原始需求已足以陈述意图、边界、父级和可验证方向，依 P-005 允许带 I-001～I-004 立项。
4. 后续实施影响治理元规则与门禁，按 P-003 判定 cross；在实施前按 P-004 向用户收集 provider。不能把其他目标的历史 provider 当作本会话指定。
5. 自动派发的输入限制不得被“补充背景”“仅审某切片”“只读这些文件”等包装绕过。审计员从正式入口自行读取权威文档并确定审计范围；独立意见落正式台账，编排器响应意见并维护状态。
6. 询问等待要求包括卡片不可用、空答复、取消、默认预选项未提交、已有目标与无目标、真实答复后恢复等边界。宿主能力须核对，不能用猜测或静态规范声称实际运行已满足。

## 判断依据与后续约束

Root [D-008](../../GOAL-001-methodology-skills-feedback-evolution/01-decision/D-008-long-running-governance.md) 允许 R3 按新反馈持续立项；Root 与 VP-002 保持 active。本目标服务现有愿景对齐链，无新 VP 或工作区需求。

此次立项采用用户明确要求的单个新目标；将两项反馈拆成两个平级目标会改变其交付组织，当前不作该选择。实施阶段如发现独立验收或并行价值，再按治理协议提出结构选择。
