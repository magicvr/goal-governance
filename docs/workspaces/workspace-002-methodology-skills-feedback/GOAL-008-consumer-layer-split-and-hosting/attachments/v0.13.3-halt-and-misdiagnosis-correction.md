# 附件 · 发版中断与一次误判的更正（2026-09-13）

> 本附件记录一次**由编排器误判引发、又由编排器自行更正**的事件。按仓库规则，真实过程不得抹去，误判与更正都要留痕。

## 1. 事件经过

1. 第一轮末，`v0.13.3` 的 annotated tag 已推送，tag workflow `34748633773` 处于 **queued**（因 GitHub runner 排队未分配；`publish` 还需 Environment `release` 人工审批）。
2. 第二轮开始，编排器在 legacy（S4 之前整份安装）迁移路径上做了一次快速探针，得到「消费者改动被静默替换」的结果，据此向用户报告**存在会丢失消费方内容的缺陷**。
3. 用户据此裁决：**停发，先修再发**。
4. 编排器立即执行：确认 `gh release view v0.13.3` = **release not found**（从未发布、无资产上传）→ 删除远端 tag（`git push origin :refs/tags/v0.13.3`）→ 删除本地 tag。工作流随之无法完成发布（tag 已不存在，且 publish 仍需人工审批）。

## 2. 误判的根因（技术）

编排器的探针把「消费者标识」放在**受管区间内部**：

```
<!-- goal-governance:begin managed -->
# AGENTS.md
- 目标记录在 workspace 根 ← 探针把 SENTINEL 插在这里（区间内）
<!-- goal-governance:end managed -->
```

`AGENTS.md` 的受管语义是「**区间外字节永不被改写；区间内由框架更新**」。因此：

- 探针把 SENTINEL 放进区间内 → 更新时按设计被框架内容替换 → 探针读出「未保留」；
- 编排器把「区间内被替换」误读成「消费者内容被静默覆盖」；
- 叠加控制台对中文的显示乱码（`Ŀ���¼��`），进一步干扰了肉眼判读。

另外，编排器在排查中曾用「替换前/后字符串对比」的自证方式，该方式本身也会把**区间内**内容算作“消费者内容”，加剧了误判。

## 3. 更正后的实测结论（可复现）

以 ASCII 形式重建四种形态，直接检验真正的不变量「**区间外字节保留**」：

| 形态 | 合并后是否改写 | 区间外字节是否保留 | 标记是否平衡 |
|------|----------------|--------------------|--------------|
| 整份 legacy 安装（区间外无内容） | 否（已收敛） | 是（无内容可失） | 1/1 |
| legacy + 消费者规则在区间**之后** | 否（已收敛） | **是** | 1/1 |
| legacy + 消费者规则在区间**之前** | 否（已收敛） | **是** | 1/1 |
| 现行标记形态 + 两侧消费者规则 | 否（已收敛） | **是**（文件未被触碰） | 1/1 |

**先前各形态 `changed=True` 的观测，来自探针自身把 `\n` 与标记拼成畸形输入所造成的失真，不是产品行为。**

**结论**：`agents_merge.py` **不存在**「legacy 迁移静默覆盖消费方内容」的缺陷；S4/S6 的不变量成立。**编排器已撤回该缺陷主张**，并把 `skills/agents_merge.py` 恢复为 tag 所指的原状（未做任何代码改动）。

## 4. 顺带确认的边界（属设计语义，非缺陷）

**受管区间内部**的文字由框架在安装/更新时替换，消费者对该区间的改动不会保留。这是 S4 模型 A 的定义性质，已写入 `skills/agents_merge.py` 模块 docstring 与 `A-014`/`A-015` 的说明；自动化探针在区间内做标记会得到「被替换」的结果，这**不是**数据丢失。

## 7. 教训（登记，供后续治理目标参考）

1. **验证前先明确不变量**：把「区间外字节保留」当成「任何标记都不许丢」，会用错探针得出错误结论，并触发一次不必要的停发。
2. **探针的判据要与文档措辞同构**：文档写的是「区间外」，探针就必须把探针数据放在区间外。
3. **控制台编码会误导人工判读**：涉及非 ASCII 的判定应改用 ASCII 哨兵或显式 `PYTHONIOENCODING=utf-8` 并打印可机读的布尔值。
4. **停发代价低、发布后回滚代价高**：本次「先确认再发」的顺序本身是对的（未产生任何已发布资产）；错的是缺陷主张的证据质量。
