# 决策记录 · GOAL-009

## D-001 · 以人机协作工作台而非只读浏览器为产品方向（2026-07-20）

**状态**：accepted

**确认来源**：用户明确要求 Web 服务于“人类工作时有 AI 协助”的目标治理，而非完善纯只读页面。

**决定**：

1. GOAL-009 规划的产品是人类主导、AI 协助的治理工作台。AI 应把 canonical 目标记录转化为有引用的上下文、候选下一步、候选文档变更和风险提示；人保有审查、编辑、拒绝、确认和裁决权。
2. 受控写入属于产品方向，但不是本轮实现承诺。任何写入须经过结构化提案、可读 diff、明确确认、协议验证、可恢复事务和可追溯的审计证据。
3. `docs/goals/` 与 `goal-tree.md` 继续是唯一运行时真相。工作台可消费和受控更新它们，但不建立第二套状态、生命周期或“AI 已完成”标记。
4. 每个 required 信息项只阻断其影响的阶段：I-001 阻断产品方案冻结，I-002 阻断 AI 接入，I-003/I-004 阻断首个 Web 写入，I-005 阻断部署或外部访问，I-006 阻断端到端验收。它们不阻断本目标的产品发现，也不要求机械等待所有项关闭后才可按已明确的最小范围立项。

**为什么**：

- 读取 Markdown 本身不能替代目标设立、决策、执行、审计与响应工作；用户需要的是更好的治理动作能力。
- 现有文档协议和 `GoalsRepository` 的事务基础可以成为可信协作面的起点，但尚不足以安全地暴露给人或 AI。
- 将人类确认和证据作为产品核心，既避免 AI 自主越权，也避免“只读”成为逃避设计真实工作流的借口。

**未选方案**：

- 把阶段 6 收敛为树浏览、Markdown 呈现和诊断打磨：价值与直接阅读文档重叠，不能推进实际治理。
- 直接把现有 service 写方法暴露为 Web/AI API：当前缺少身份、授权、确认、溯源、并发和安全失败机制。
- 让 Web 或模型维护独立状态：会违背 canonical 文档真相源并造成同步漂移。

**影响与后续**：本决定引用根 D-014。I-001～I-006 的收集结果将决定第一个实现目标的边界；本轮不宣称任何产品功能或安全控制已完成。

## 信息需求与阶段门禁

本目标的唯一信息台账位于 [00-meta.md](00-meta.md#信息就绪与未知项)。实施、部署和验收门禁以该表为准；没有 residual risk 接受。

## D-002 · 将第一阶段限定为单用户、多工作区、事实确认的工作台（2026-07-20）

**状态**：accepted

**确认来源**：用户在本目标的独立审计请求中明确给出 Web 第一阶段的产品边界，并授权在不符合时修正计划。

**决定**：

1. 第一阶段面向一名用户，不考虑多用户、协作、账号、角色或权限管理。目标负责人、审计等保留为治理工作流的语义视角，而不是系统中的人或授权角色；P-004 仍由这名用户作出明确裁决。
2. 事实的准入权在用户。AI 可以在用户要求或确认的范围内调用网络工具、本地自动化或知识检索，也可以基于已确认信息提出推导；但这些结果必须以候选形式显示来源、时间和引用或推导链，并经用户显式确认后才可写成 canonical 事实、证据或风险结论。没有来源或确认的内容不得由 AI 编撰为事实。
3. 工作台应自动复用本工作区已确认的 canonical 信息。纯读取或计算视图可明确标为“计算得出”而不重复向用户索取文本；任何要进入长期记录的新增事实仍须经过第 2 项的确认链。
4. 一个工作区对应一个独立根目标和 canonical 范围。工作区之间不能读取、写入或混合 AI 上下文；平台级工作区索引仅用于导航，不得维护第二套目标状态。具体存储拓扑、根目标命名空间和生命周期仍由 I-009 收集后冻结。
5. 贡献资料区在工作区之外，允许用户上传并让多个工作区只读引用特定版本。工作区可写自己的资料引用、注释和已确认的派生记录，但不能修改资料原件、资料版本或其他工作区内容；具体资料治理由 I-010 决定。
6. 第一阶段的信息架构至少包括总览页、工作区列表页和以目标树为核心的工作区详情页。详情页必须能通向本工作区的事实确认、资料引用、门禁、审计和受控变更；具体首个用户旅程由 I-011 审视。

**为什么**：

- 这组边界让工作台先减少单个用户治理闭环中的重复输入与上下文切换，而不提前引入多租户、协作权限或跨工作区同步复杂度。
- 将“AI 候选”和“用户确认的事实”分开，才能同时利用检索/自动化能力和保持 `docs/goals/` 事实记录可信。
- 多工作区与贡献资料是不同的数据边界：前者要求目标状态与上下文隔离，后者只提供可追溯的共享读取，不能成为绕过工作区写入约束的通道。

**未选方案**：

- 用负责人、协作者、审计者建成第一阶段的多角色权限模型：与单用户范围冲突，并会在未验证价值前引入不必要的身份与授权设计。
- 让 AI 搜索、知识回答或推导自动写入事实：会把未验证信息伪装为用户确认的记录，违背本项目的证据与 P-005 门禁。
- 让所有工作区共同使用一份可写目标树，或让贡献资料可被工作区任务修改：会破坏根目标隔离、写入可追溯性和资料版本稳定性。

**影响与后续**：

- 本决定修正 `00-meta.md` 中原先“负责人、协作者和审计者”的多角色表述，并新增/细化 I-008～I-012。
- 它只确定产品边界，不宣称工作区、资料区、AI 检索、确认链或页面已实现；I-001～I-006、I-008～I-011 仍为 collecting 的 required 信息。
- 本轮独立审计的 findings 仍须由 `/govern` 汇总、响应并以可核对证据关闭；本决定不改变目标 status 或 progress。

## D-003 · 将 R-001 组织为待用户审视的单用户三页最小旅程（2026-07-20）

**状态**：proposed

**确认来源**：用户要求优先收集 I-001/I-011，并先形成单用户工作流、三页信息架构和最小垂直旅程。

**决定**：

1. 将 I-001 与 I-011 作为同一 R-001 收集项处理，产出一份可审视的候选设计，而不是分别零散记录页面或功能清单。
2. 候选信息架构固定为三个顶层页面：总览、工作区列表、以目标树为核心的工作区详情。事实候选、贡献资料引用、门禁、审计和受控变更均是工作区详情中的上下文面板或动作入口，不额外宣称为顶层页面。
3. 候选最小垂直旅程限定为：进入一个既有工作区的目标树 → 选定目标并基于 canonical 上下文形成候选事实 → 用户编辑、拒绝或要求形成受限变更提案 → 查看受影响 canonical 记录的 diff 与门禁 → 经明确确认后显示受控结果和证据。该旅程只界定产品意图；确认状态机、基线绑定、operation id、并发/幂等和实际写入协议仍由 I-003/I-004/I-006 收集，不能据此开放写入。
4. 设计稿必须明确单一用户、无账号/协作/角色模型、无 AI 自动写入或裁决、无跨工作区上下文混合，以及贡献资料只读引用的方向性边界。

**理由**：

- A-004 的 R-001 要求把 F-001/F-005 的工作流与三页旅程形成可由用户审视的共同证据；将两项分离会丢失页面导航、候选确认与最小场景之间的依赖。
- 以既有工作区中的一次窄事实确认作为候选首切片，可验证工作台是否减少上下文切换，而不会把多工作区、资料库、AI 提供方和完整写入系统一次性当作首个实现范围。
- 将结果保持为 `proposed` 可避免把本轮设计输入误写为用户已接受的产品方案、路线图 A 退出或 required finding 的关闭证据。

**未选方案**：

- 直接把现有只读首页和单目标详情命名为三页工作台：当前没有工作区选择、确认或受控变更入口，且不能满足 F-005 的审视要求。
- 将事实确认、资料引用、门禁、审计和受控变更各自扩展为独立顶层页面：会在尚未验证首个闭环前扩大导航和实现范围。
- 以 AI 自动抓取或直接写入作为最小旅程：会越过用户触发、候选呈现、显式确认和 I-003/I-004 的开放门禁。

**影响与后续**：

- 候选设计见 [R-001 收集稿](attachments/r-001-single-user-workflow-ia-vertical-journey.md)。I-001/I-011 保持 `required / collecting`，直至用户审视并留下可核对结论；F-001/F-005 仍开放。
- 不改变 GOAL-009 的 `status`、`progress` 或路线图阶段；不立项实现、不修改 `web/`，也不把该文档当作 I-003/I-004/I-006 的确认或写入契约。
