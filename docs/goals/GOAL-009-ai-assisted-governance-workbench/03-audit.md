# 审计 · GOAL-009

## 当前审视状态

本目标已形成两条 independent 意见（A-001/A-002）、一次同范围 self 审视（A-003）及其合并响应（A-004），结论均为 `conditional`。F-001～F-005、F-007/F-008 仍为开放 required findings；没有 residual risk 接受、finding 关闭证据或阶段放行。

当前焦点为 R-001：收集 I-001/I-011 的单用户工作流、三页信息架构和最小垂直旅程，并由用户审视。后续审视至少核对：

- I-001～I-006 是否在其最晚需要阶段前有可核对证据；
- AI 建议、人类确认、P-004、状态/关门门禁是否被明确区分；
- canonical 文档、事务/恢复和审计证据是否不会被 Web 的便利性绕过；
- 任何实现声明是否有测试、可用性或实际试点事实支撑。

## A-001 · Web 第一阶段产品边界与计划一致性审计（2026-07-20）

- **source**：independent
- **auditor**：Codex
- **类型**：design-plan
- **scope**：核对 GOAL-009 的产品定义、路线图和信息门禁，是否符合用户于 2026-07-20 明确的第一阶段边界：单用户无多角色、事实不由 AI 编撰、AI 引导并复用上下文、多工作区根目标隔离、共享只读贡献资料区，以及总览/工作区列表/工作区详情三类页面。
- **verdict**：conditional

### 范围与证据

- [00-meta.md](00-meta.md) 原始成功标准把“负责人、协作者和审计者”列为核心工作流，而没有单用户或无角色边界；原始路线图和信息台账也没有工作区、共享资料或事实确认模型。
- [D-001](01-decision.md#d-001--以人机协作工作台而非只读浏览器为产品方向2026-07-20) 已正确确立“人主导、AI 协助”“引用 canonical 记录”“明确确认”和“不得建立第二状态源”的方向，但没有把本次的产品约束变成可验收的模型。
- [02-execution.md](02-execution.md) 如实记录当前 Web 仍只有目标概览/详情读取，未实现 Web 写入、身份/确认、AI 服务或提案溯源。架构概览也将当前 Web 定义为只读/诊断消费适配器。
- 核心原则 P-002～P-005 要求事实可指回证据、独立审计只出意见、用户确认 P-004 裁决并在 required 信息项的最晚阶段前取得证据；本审计按这些约束评估计划，未把本次计划文字修订当成实现证据。

### 已符合的方向

1. `docs/goals/` 与 `goal-tree.md` 仍是 canonical 真相源，AI 不可自动关门、自动裁决 P-004 或绕过受控写入；这与用户要求“AI 不编撰事实”的治理方向一致，但不足以构成事实准入模型。
2. AI 使用引用的上下文提出下一步、候选文档变更和风险提示，人保有审查、拒绝和确认权；这为“减少重复输入”提供了正确起点，但尚未规定上下文复用、自动获取信息和确认链。
3. 现有 Web 已有只读概览和单目标详情基础，但没有 workspace 实体、工作区列表或工作区详情层级，不能满足多工作区产品模型。

### Findings

#### F-001 · 单用户无角色边界与原计划冲突

- **级别**：required；**严重度**：high
- **关联信息项**：I-001、I-003
- **证据**：原成功标准要求“负责人、协作者和审计者”的核心工作流；用户明确要求暂不考虑多用户和多角色。
- **影响**：若继续以角色为模型，后续会错误引入账号、授权、协作状态和审计主体设计，偏离第一阶段的最小范围。
- **关闭要求**：在路线图 A 结束前，将工作流改为单一用户可切换的治理视角，写清不做的多用户/多角色能力，并以页面场景审视该边界。

#### F-002 · 事实来源、候选与显式确认未形成可验证模型

- **级别**：required；**严重度**：high
- **关联信息项**：I-002、I-004、I-006、I-008
- **证据**：D-001 只要求 AI 提供“有引用的上下文”和人确认；它未定义用户提供、网络检索、知识回答、逻辑推导之间的来源字段、候选状态、确认/拒绝/撤回、时间和推导链。
- **影响**：AI 很容易把未确认的检索结果、模型知识或推论混入执行事实、审计结论或风险关闭证据，直接违背本次用户要求和 P-002/P-005。
- **关闭要求**：在路线图 B 结束前，以数据和交互契约覆盖上述来源、候选、确认与撤回路径，并对“无来源”“未确认”“来源变更”运行负向验证。

#### F-003 · 多工作区根目标隔离缺失

- **级别**：required；**严重度**：high
- **关联信息项**：I-004、I-006、I-009
- **证据**：现有运行模型是单一 `docs/goals/` 实例；GOAL-009 原计划没有 workspace、独立根目标、工作区索引、跨工作区访问规则或 AI 上下文隔离。
- **影响**：共享一棵可写目标树会使目标 ID、上下文、事务、审计记录和恢复责任相互污染，并可能把平台索引误做成第二状态源。
- **关闭要求**：在路线图 B 结束前，选择并验证工作区到独立 canonical 根目标的映射、索引边界、创建/归档生命周期和跨工作区读写拒绝策略；不得把储存拓扑猜测为已定方案。

#### F-004 · 共享贡献资料区的数据所有权和只读语义缺失

- **级别**：required；**严重度**：high
- **关联信息项**：I-010、I-006
- **证据**：当前附件仅属于单个目标；原计划没有共享资料、版本、引用、可写边界、资料溯源或不可信内容处理。
- **影响**：若工作区可直接改写共享资料，或引用不固定版本，资料会成为跨工作区的隐式可写状态和不可复核证据来源。
- **关闭要求**：在路线图 B 结束前，定义用户上传、资料版本/哈希、只读引用/固定、工作区本地注释、保留删除和不可信内容处置；用跨工作区正反访问测试证明写边界。

#### F-005 · 三页信息架构和首个端到端旅程尚未定义

- **级别**：required；**严重度**：medium
- **关联信息项**：I-001、I-011
- **证据**：现有 Web 只有单实例的首页和 `/goals/{goal_id}` 详情；原计划没有总览、工作区列表、工作区详情之间的导航和确认入口设计。
- **影响**：即使底层模型正确，也无法验证用户能在多个工作区中定位目标、复用上下文、确认候选事实并完成一个闭环。
- **关闭要求**：在第一个实现子目标立项前，审视页面信息架构、状态/空态/失败态和一个端到端用户旅程；目标树必须是工作区详情的核心而非附属页面。

#### F-006 · 试点运行保障需在设计中保留，但可后置验证

- **级别**：recommended；**严重度**：medium
- **关联信息项**：I-005、I-006、I-012
- **证据**：现有计划覆盖部署与 fail-closed，但尚未明确 AI 不可用时的非 AI 路径、用户可见的活动记录、无障碍/本地化、导出/保留，以及贡献资料可能包含的提示注入或敏感内容。
- **影响**：这些问题不应阻断当前产品发现，但若在首次试点前仍未明确，会降低用户对确认、恢复和资料边界的可理解性。
- **建议**：将其保留在 I-005、I-006、I-010、I-012 的设计/试点检查中，并在实现目标的验收标准中给出可观察的失败与恢复行为。

### 必改项汇总与门禁

| Finding | 结论 | 阻断门禁 | 当前关闭证据 |
|---------|------|----------|--------------|
| F-001 | 单用户、无角色的范围必须替代原角色模型 | 路线图 A 退出 | 尚无经 `/govern` 审视的场景证据 |
| F-002 | 事实准入、来源与显式确认必须先于 AI 协作设计冻结 | 路线图 B 退出 | 尚无数据/交互契约或负向验证 |
| F-003 | 多工作区的独立根目标和隔离模型必须先于实现范围冻结 | 路线图 B 退出 | 尚无储存拓扑、索引边界或隔离测试 |
| F-004 | 贡献资料区的只读、版本和引用规则必须先于资料读取/写入设计冻结 | 路线图 B 退出 | 尚无资料模型或访问测试 |
| F-005 | 三页信息架构和端到端旅程必须先于首个实现子目标立项 | 路线图 D 立项 | 尚无页面/状态设计或用户旅程审视 |

### 本轮计划修订与审计边界

用户明确授权“若不符合则修正”。该授权已被记录为 [D-002](01-decision.md#d-002--将第一阶段限定为单用户多工作区事实确认的工作台2026-07-20)，并已据此修订 [00-meta.md](00-meta.md) 和 [02-execution.md](02-execution.md)。这些是范围和信息登记的修正事实，不是对 F-001～F-005 的自动关闭：每项仍需要 `/govern` 汇总、针对关联 I-00N 的可核对设计/验证证据，并在适用时复审。

### 与既有意见的关系

本目标此前没有 `A-00N` 条目，无同范围的 self 或 independent 意见可冲突。本条是第一条独立意见；由于尚无 self 审视，后续要推进相关门禁时应由 `/govern` 按 P-004 询问用户是否需要自审。

### 结论与建议的下一步

GOAL-009 的方向正确，但原计划不足以作为第一阶段产品方案冻结的依据，故 verdict 为 **conditional**。优先通过 `/govern` 将本轮用户边界和 A-001 一并响应，先收集/审视 I-001、I-008、I-009、I-010、I-011，再决定是否进入路线图 B；不要因为文字计划已修订而提前立项实现或开放 Web/AI 写入。

### 声明

本独立意见不改变 GOAL-009 的 `status` 或 `progress`，也不把任何 required finding 标为已关闭。状态推进、finding 响应和自审选择归 `/govern` 与用户。

## A-002 · Web 工作台产品设想合理性审计（2026-07-20）

- **source**：independent
- **auditor**：Codex
- **类型**：design-plan
- **scope**：独立判断 GOAL-009 对 Web 的整体设想是否形成合理、可实施且不破坏 canonical 治理协议的产品方向；重点核对产品价值、范围收敛、现有 Web 基础、AI 事实准入、多工作区/贡献资料边界，以及受控写入的确认、并发和恢复语义。
- **verdict**：conditional

### 范围与区间

- 本意见审计当前 [00-meta.md](00-meta.md)、[01-decision.md](01-decision.md)、[02-execution.md](02-execution.md)、既有 [A-001](#a-001--web-第一阶段产品边界与计划一致性审计2026-07-20)、根目标 D-014、架构边界及现有 `web/` 代码。
- 审计对象是产品设想和计划是否合理，不审计尚未发生的实现、试点或关门事实。
- A-001 的 F-001～F-005 仍是开放 required findings；本意见不因计划文字已经补齐而将其关闭。

### 成果与合理判断（有证据）

1. **产品方向合理**：从纯只读浏览器转为人类主导、AI 协助的治理工作台，解决的是“理解上下文、形成候选动作、审查并确认变更”的闭环问题，而不是重复展示 Markdown。根 D-014 与 D-001 对该价值和边界的表述一致。
2. **真相源边界合理**：`docs/goals/` 与 `goal-tree.md` 保持唯一运行时真相；Web 参与受控变更但不拥有独立生命周期、状态数据库或“AI 已完成”标记。这与“三层交付、一个真相源”一致。
3. **AI 权限边界合理**：AI 只能提出带来源或推导链的候选，人可以编辑、拒绝和确认；AI 不得自动裁决 P-004、关闭 required finding、标记 `done` 或把未确认信息写成事实。
4. **单用户与多工作区并不矛盾**：第一阶段不做多用户、协作和角色权限，可以显著降低产品复杂度；同时以工作区隔离不同根目标、以贡献资料区提供版本固定的共享只读输入，是合理的数据边界。
5. **路线图顺序基本合理**：先完成工作流与信息就绪，再定义读模型、AI 协作和受控变更契约，最后另立实现目标，符合 P-001/P-005；当前 `0%` 也没有把仓储层的写入与 recovery 基础误记为产品能力。

### 现有实现基础与真实落差

- 当前 HTTP 层只有首页和目标详情 GET 路由，旧 decision/execution/audit 路由仅重定向；没有 workspace、AI、确认或写入 API。
- `GoalsRepository` 已提供五件套解析、目标树诊断、Create/Update、文件替换与 recovery，可作为后续实现基础；但没有 approval、provenance、workspace lock、条件写入或幂等操作语义。
- 因此“可复用基础存在”支持该方向的可行性，但不能证明 GOAL-009 的产品契约已经完成，也不能直接开放现有 service 写方法给 Web 或 AI。

### Findings

#### F-007 · 单用户边界尚未转化为可验证的确认与信任边界

- **级别**：required；**严重度**：high
- **关联信息项**：I-003、I-005、I-006
- **证据**：I-003 已登记现有 Web 无认证、会话或写入路由，并计划定义单用户确认状态机；D-002 只排除了多用户/多角色，尚未定义一次确认如何绑定到具体工作区、目标、输入快照、diff 和用户动作。
- **风险**：即使只有一名用户，过期页面、重复提交、跨工作区请求、CSRF/本地恶意页面、外部访问或确认前内容变化，仍可能使“用户确认”与实际写入内容脱节。单用户不是省略信任边界的理由，也不要求反向引入多角色模型。
- **关闭要求**：路线图 C 退出前定义可测试的操作/确认状态机，至少绑定 workspace、目标、canonical 基线版本或哈希、提案/diff、确认动作、有效期和 operation id；对拒绝、撤回、过期、重放、内容变化、未授权和跨工作区请求运行 fail-closed 负向验证，并按本地/受控外部部署分别写清信任假设。

#### F-008 · 文件级 recovery 不足以证明受控写入与审计证据的原子一致

- **级别**：required；**严重度**：high
- **关联信息项**：I-004、I-006
- **证据**：现有 repository 使用临时文件、`os.replace`、备份和 recovery record 处理写入失败；I-004 已承认缺少锁定、approval、provenance 和幂等语义。当前计划尚未规定两个请求/进程并发、相同操作重放或恢复后，canonical 五件套、`goal-tree.md`、确认记录和审计关联如何保持同一次操作的一致身份。
- **风险**：单次文件替换可回滚，不等于跨文件、跨请求的条件写和审计原子性；并发覆盖或恢复后证据断链会让用户无法证明“确认的 diff 就是最终写入的 diff”。
- **关闭要求**：路线图 C 退出前定义 per-workspace 串行化或乐观版本检查、operation id 幂等、冲突拒绝、变更包与确认/审计关联，以及恢复后的可核对结果；用并发提交、重复提交、进程中断、部分替换和 recovery 重放测试验证，而非只测文件替换异常。

#### F-009 · 首个实现切片仍有被全量产品模型拖宽的风险

- **级别**：recommended；**严重度**：medium
- **关联信息项**：I-001、I-011
- **证据**：路线图 B/C 同时覆盖多工作区、贡献资料、AI 上下文、事实确认、受控写入、事务/恢复、部署和失败安全；I-001/I-011 尚未给出一个经用户审视的首个垂直场景。
- **风险**：如果把上述所有能力都当作第一个实现目标的完整功能，而不是边界契约和分阶段能力，产品发现会转为长时间抽象设计，难以及早验证工作台是否真的减少上下文切换并改善一次治理动作。
- **建议**：路线图 A 结束前冻结一个窄而真实的垂直闭环，例如“进入一个工作区的既有目标 → 基于 canonical 上下文形成候选变更 → 用户编辑/拒绝/确认 → 展示并执行一个受限 canonical 变更 → 在同一页面核对结果与证据”。多工作区至少保留隔离的正反验证，贡献资料和真实 AI 提供方只纳入该切片确有需要的最小能力；其余能力按后续实现目标展开，不降低 I-009/I-010 的边界设计门禁。

### 对照初始成功标准

| 方面 | 判断 | 说明 |
|------|------|------|
| 产品价值与非目标 | 合理但未验证 | 已明确不是只读终态、不是 AI 自治代理；首个可验证场景仍由 I-001 收集。 |
| canonical 与事实准入 | 方向合理、不可冻结 | 边界正确；A-001 F-002 与 I-008 尚无数据/交互契约和负向验证。 |
| 多工作区与贡献资料 | 架构意图合理、不可冻结 | 隔离与只读引用的原则成立；A-001 F-003/F-004 尚无拓扑、版本和访问测试。 |
| 页面与用户旅程 | 结构合理、不可立项 | 三类页面与目标树核心符合工作流；A-001 F-005/I-011 尚无完整旅程与状态设计。 |
| 受控写入 | 必要且高风险 | 现有 service 是基础，不是产品级确认、并发、幂等与审计原子性证据；F-007/F-008 阻断路线图 C 退出。 |
| 实施节奏 | 基本合理、需进一步收敛 | 规划目标和实现目标分离正确；应按 F-009 先冻结一个垂直闭环。 |

### 必改项汇总与门禁

| Finding | 结论 | 阻断门禁 | 当前关闭证据 |
